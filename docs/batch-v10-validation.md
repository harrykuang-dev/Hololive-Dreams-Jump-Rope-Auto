## 為何遊戲 60 FPS，程式只有約 28

60 FPS 每輪預算是 16.67 ms。v9 七局每項耗時中位數範圍：

| 項目 | 耗時 |
| --- | --- |
| PrintWindow 捕獲整項（含配置與拷貝） | 24.14–24.42 ms |
| HUD／角色檢查 | 1.98–2.03 ms |
| 繩線辨識 | 7.10–7.36 ms |
| 背景編碼 | 2.39–2.57 ms（非同步，queue_peak=1） |
| 捕獲時間戳到實際起跳按下 | 38.07–39.02 ms |

捕獲一項就超過整幀預算，串行加上辨識不可能達到 60。起跳前額外捕獲複查、
25 ms 按鍵保持也會使少數迭代更慢。不是把 MP4 fps 改成 60 就能拿到 60 個新畫面。
[Microsoft PrintWindow 文件](https://learn.microsoft.com/en-us/windows/win32/api/winuser/nf-winuser-printwindow)
說明它是同步呼叫並由目標應用繪製；此處 24 ms 是本專案的實測整項，不是所有電腦通用值。

v10 預設改試 [BitBlt](https://learn.microsoft.com/en-us/windows/win32/api/wingdi/nf-wingdi-bitblt)
複製可見客戶區，重用 bitmap/DC；移除遊玩開始後重複的開局 HUD 查詢。
仍逐次檢查焦點，擷取前後確認螢幕內完整客戶區與上方視窗遮擋；位置／尺寸在擷取中
變動即停止。結束、錯誤、批量等待退出時釋放資源。沒有背景快取幀、沒有以舊畫面代替
起跳前複查，沒有為提高數字而取消安全檢查。舊相容路徑可選 `--capture printwindow`。
**新的即時捕獲速度、GPU／合成器相容性尚未驗證，不能宣稱已達 60 FPS。**

## 遮擋定位與修改

- 已定位 21 次扣血。仍存在反向時機錯誤、暗繩被道具遮住後無法重新待命、玩家標記
  複查失敗而拒絕輸入等不同原因，不能把所有扣血都歸因於 FPS。
- 第 1 局 t=72.9075／83.9617，貼地繩的量測從高點突然掉到碗邊；隨後回到繩上，
  舊邏輯把它當作反彈，於 72.979／83.989 提早用掉本圈回程觸發。
- v10 對近端高點的低置信度曲線加入有上限的連續性懲罰：選的仍是本幀可見像素
  支持的曲線，不推算被遮住的繩，不增加置信度。另在貼地狀態拒絕低置信度突降
  形成谷點，保留後續真實回程的資格。
- 原始量測回放移除上述兩個提早觸發，後續 73.275／84.2392 各保留一個候選。
  是否剛好落在遊戲容錯窗仍需实戰，不能宣稱已救回生命。
- 新增九幀 PNG 回歸：frame 2232 中央被碗蓋住，但左右繩段仍支持約 .13 的高點。
  短序列未修正量測約 .047，新版約 .123；保留當前像素置信度約 .515。
- 曾把連續性套在整個弧線上，完整回放第 5 局 t=35.8058 多出候選；已拒絕此方案，
  最終僅套用近端高點。沒有放寬全域起跳線、沒有固定間隔或預定加速補跳。
